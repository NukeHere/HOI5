# Алгоритмы игровых ИИ и первая версия для HOI5

Исследование от 2026-10-31. Изучены опубликованные разработчиками материалы и открытые исходники. Это проект адаптации; замеры производительности нового ИИ ещё не проводились.

## Границы исследования

- HOI4: опубликованные объяснения разработчиков, не полный закрытый код движка. Описания привязаны к дневникам 2021, 2023 и 2024 годов, а не заявлены полной спецификацией последнего патча.
- Civilization: конкретно код игровой DLL Civilization V из SDK в публичном зеркале Gedemon. Не смешивать его с модом Vox Populi и не переносить автоматически на Civ VI/VII.
- Supreme Commander: конкретно открытые Lua-файлы Forged Alliance Forever с унаследованной и изменённой логикой. Не выдавать эту ветку за неизменённый исходный Supreme Commander.
- StarCraft: отдельно встроенные скрипты Brood War по материалам Blizzard и отдельный исследовательский бот UAlbertaBot. BOSS и SparCraft не являются доказательством устройства штатного ИИ Blizzard.
- Rusted Warfare: открытый интерфейс настройки ИИ по справочнику, на который ссылается сайт разработчика. Он не раскрывает полностью планировщик или выбор боевой цели.

## Минимальная архитектура

```text
aggregate_facts → observer_report → assessments → regional_demands
               → eligible_tasks → assignments → validated_commands
```

Не требуется сначала переписать весь сервер, все существующие системы или построить универсальный планировщик. Наблюдательную первую версию можно подключить к текущему обновлению симуляции. Общую границу команд расширять по мере подключения конкретных действий. Корректное поведение при крупных шагах времени проверять отдельно; новый планировщик не исправляет автоматически существующую точность времени.

Достаточно начать с моделей и нескольких функций в 3–4 модулях: `ai_models.py`, `ai_assessment.py`, `ai_regions.py`, `ai_scheduler.py`. Разбивать дальше, когда появляется реальная ответственность. Отдельный слой условий не обязан быть новым языком, DSL, сложным деревом поведения или системой плагинов.

### Агрегаты и разведка

Сначала один общий проход по миру на расчётную дату: обновить точные вклады районов/стран. Свои оценки берутся напрямую; иностранные проходят фильтр. Повторные наблюдатели не запускают пересчёт производства каждой страны заново.

Хранить краткую историю агрегатов, а не копии всей карты. Для первой разведки достаточно одного сохранённого пакета на пару наблюдатель/цель и несколько прошлых сводок цели. Качество задавать по группам показателей; устойчивое отраслевое смещение получать один раз на донесение. Нижнюю/верхнюю оценки можно строить лениво из значения, качества и давности.

Сначала периодический расчёт надёжнее сложных дельт без полной системы событий. Когда измерения покажут стоимость, внедрять грязные районы и кэш вкладов: `новый агрегат = старый - старый вклад + новый вклад`. В периодических полных сверках обнаруживать пропущенные изменения. Боевые/производственные фактические счётчики добавлять в существующие точки исполнения без необходимости полного event bus.

### Кандидаты задач

```text
TaskTemplate:
    kind
    cheap_applicability(region, country)
    utility(region, country, strategic_weights)
    feasibility(candidate)
    cost_and_assets(candidate)
    max_active
    retry_delay
    completion_condition
```

Сначала жёстко отфильтровать невозможное. Затем оценить дешёвые нормированные признаки. Подробную реализуемость и гекс размещения проверять для нескольких лучших кандидатов. Приоритеты вычислять из снимка, не изменяющего мир.

Для проверки нормы `объектов_нужно - (работают + строятся + уже назначены)` учитывать состояние/мощность объектов и отменённые задачи. Стройка с нулевым шансом завершения не должна навсегда закрывать реальную потребность. При этом новый кандидат не должен дублировать ещё действующую задачу.

### Районы и размещение

Базовый вариант географии — многоточечный поиск по графу проходимости с устойчивыми центрами. Разделение слишком большого района выполнить в отдельном ограниченном проходе. Основной пересчёт районов — при генерации/редком изменении разбиения; владение хранить отдельно. Не создавать новый набор районов для каждого бота по его экономическим предпочтениям.

Микро выбирает гексы внутри заданного района: дешёвый просмотр допустимости и простой пользы, затем точная проверка нескольких лучших. Для малого района достаточно полного просмотра его гексов; не нужны сложные индексы, пока замер не покажет пользу.

### Распределение сил

```text
для района:
    оценить угрозу на горизонте
    определить минимальный полезный состав
    определить желаемые возможности и верхний предел полезного усиления

сначала закрыть критические обязательства доступными подходящими силами
затем сформировать несколько выполнимых пакетов усиления/операций
сравнить пользу пакетов с учётом времени подхода и цены переброски
выделить лучшие в пределах ресурсов
оставить центральный резерв
```

При нехватке сил явно ранжировать потери, а не размазывать армию по невыполнимым минимумам. Жадный выбор допустим как первое приближение, но для комплементарных ресурсов нужен пакет: отдельная пехота или ПВО могут не решить задачу, а совместное усиление — решить.

### Локальные военные оценки

Уровень 1: дешёвый профиль района и противника. Уровень 2: несколько лучших доступных групп и направлений. Уровень 3: короткая чистая приближённая модель только для спорного важного столкновения. Не копировать мир и не запускать настоящий боевой тик над игровыми объектами при оценке.

Первая версия обходится без SparCraft-подобного поиска управления отдельными единицами и без дерева всех последовательностей строительства. Учитывать боевые ограничения из текущей игры, а затем сравнивать прогноз с фактическим исходом и исправлять систематические ошибки.

### Зависимости и влияние

Первый экономический рычаг — доля критической поставки, запас в днях и оценка замены. Полный прогноз цепочек запускать для нескольких важных зависимостей при существенном изменении. Не считать все сценарии всех стран каждый шаг. Политическое влияние остаётся оценкой конкретного решения; культурные каналы требуют собственной будущей механики.

## Стоимость вычислений

Обозначения: N — гексы, U — соединения, C — страны, D — координаты профиля, R — районы, P — рассматриваемые сценарии.

| Операция | Предлагаемая стоимость/частота |
|---|---|
| Сбор текущих сил | O(U), один общий проход по расчётной дате |
| Первичные пространственные агрегаты | O(N × локальные признаки), периодически или по изменениям |
| Пакеты иностранных оценок | O(C²D) в даты донесений; без повторного сканирования гексов |
| Разбиение графа на районы | Один многоточечный проход O((N+E)log N); дополнительные разбиения отдельно |
| Выбор простых районных задач | O(R × число применимых шаблонов) |
| Детальные сценарии | Ограниченный P; считать по агрегатам, не по всему миру |
| Поиск маршрутов | Только для отобранных назначений, с лимитом и очередью |

При 12 странах и 100 координатах 132 направленные иностранные оценки содержат 13 200 значений. Это лишь размер числовой таблицы: он не измеряет стоимость Python-объектов, историй, агрегации и поиска пути. Главные кандидаты на дорогие операции — пространственный поиск, повторные сканирования и локальные прогнозы.

Не начинать с обновления всех дельт, плотной матрицы всех пар гексов, многопоточности или обязательного NumPy. Обычные списки/словари с ограниченными проходами подходят для прототипа; менять представление после профилирования.

## Планирование вычислений

Решения привязаны к игровому времени. Тяжёлые независимые расчёты можно продолжать порциями, но их результаты вступают в силу на фиксированной логической границе после подготовки необходимых данных. Быстрый компьютер не должен получать дополнительные игровые решения только потому, что успел больше за кадр.

Срочные проверки дешевле обычного перепланирования и имеют зарезервированную долю работы. Просроченность задач измеряется; нельзя просто бесконечно откладывать последнего бота. Если обработка всей симуляции не успевает за выбранной скоростью, показывать фактическое замедление, а не пропускать обязательные шаги/события молча.

Начальные игровые интервалы: срочные локальные проверки — на доступном базовом шаге, региональная военная оценка — порядка 6 часов, экономика и макрозадачи — сутки, иностранная экономика — несколько дней, стратегия — месяц плюс важные события. Это настройки, не подтверждённый баланс; текущий крупный шаг мира ограничивает точность реакций.

## Как проверять результат

Замерить одинаковые сиды и входные условия: без нового ИИ, со сбором оценок, затем с решениями. Отдельно фиксировать общий шаг мира, слои ИИ, память/размер истории, среднее, высокий процентиль, максимум и задержку решения по игровому времени. Карты и количество ботов брать из реальных игровых настроек; отдельно максимальная скорость и длительный прогон.

Для первого этапа разумно поставить предварительную цель порядка нескольких процентов дополнительной стоимости симуляции на тестовом сценарии, но принять конкретную границу только после базового замера. Это не обещание достигнутого FPS. Нагрузка должна оцениваться также в абсолютных миллисекундах и игровых днях за реальную секунду, особенно если исходная симуляция уже не укладывается в бюджет.

Качество: доля невыполнимых/повторных приказов, предсказанные и реальные дефициты, осмысленность размещения, частота смены курса, сохранение резервов, исход локальных сценариев. Улучшение общей статистики побед не заменяет проверку конкретных причин решения.

## Ближайшие результаты по порядку

1. Небольшая диагностическая сводка страны: мощности/факт/запасы/торговля и военный состав, с источниками и единицами.
2. Устойчивые районы и их агрегаты.
3. Сохранённые разведывательные пакеты и дешёвые оценки дефицита/угроз.
4. Минимальный набор районных требований и объясняемый выбор ограниченных задач.
5. Выбор конкретного гекса/назначения и проверяемая команда.
6. После измерений — детальные сценарии, более качественная концентрация сил и дополнительные дипломатические каналы.

Каждый результат должен отдельно работать и измеряться. Полное воплощение концептуального документа не является условием появления первого полезного поведения.
